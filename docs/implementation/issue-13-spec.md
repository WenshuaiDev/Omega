# Omega 工程基座 V1 开发规格

## Problem Statement

Omega 需要一套与具体业务无关的工程基座，使开发者在拉取代码后，通过一个明确入口完成首次准备并启动整个项目，同时支持多个前端应用、后端应用维护，以及开发、测试、生产三种环境。

当前仓库只有协作约定及本次讨论形成的文档，没有可复用的工程实现或测试体系。若缺少统一契约，开发者将不得不手工准备配置、安装依赖、初始化数据库和启动多个进程；部署方也无法确认现场镜像、环境配置和已验证版本是否一致。

测试和生产环境不能依赖外网，需要通过文件传入完整发布物。工程基座必须让正常操作可重复、失败行为可诊断、数据和实例边界明确，并避免将应用运维命令扩展成另一套工程管理平台。

## Solution

建设基于 Go Workspace、React、Vite、TypeScript、Yarn Workspaces、Docker Compose 和 Nginx 的单仓库工程基座。以一个 api 服务、web 和 console 两个参考应用以及 PostgreSQL 验证能力，不预设业务功能。

开发者执行 `make dev` 即可完成开发环境准备、应用迁移、必要系统元数据初始化、启动和入口验证。应用运维 CLI 命名为 `omega`，随 `omega-api` 同版本、同镜像交付。

开发及构建允许联网；test/prod 采用 Linux amd64 单机离线部署。操作者手动运行统一的检查、构建、打包和部署脚本，将同一组已验证镜像从 test 提升到 prod。正式部署允许维护窗口，失败时保留数据及诊断；仅在确认兼容时允许应用版本回退。

本规格不包含 CI 或备份恢复。当前交付仅为规格文档；用户明确要求暂不实施，发布本 Issue 不代表启动开发。

## User Stories

1. 作为开发者，我希望通过一条 `make dev` 命令完成首次准备和启动，以便不必记忆多套手工步骤。
2. 作为开发者，我希望无需在宿主机安装 Go、Node、Yarn 和数据库，以便开发依赖由项目容器统一提供。
3. 作为开发者，我希望缺少 Docker、Compose 等前置条件时得到明确错误，以便直接处理真正的启动阻碍。
4. 作为开发者，我希望 api、两个参考应用、入口代理和数据库一起启动，以便获得完整开发链路。
5. 作为开发者，我希望启动成功后看到可访问地址并返回终端，以便继续正常开发。
6. 作为开发者，我希望重复执行启动命令保留配置、密码和数据，以便安全协调已有环境。
7. 作为开发者，我希望前端源码修改经统一代理触发热更新，以便浏览器入口与实际开发方式一致。
8. 作为开发者，我希望 Go 源码及实际共享依赖变化触发重编译，以便及时运行新代码。
9. 作为开发者，我希望编译失败明确显示，以便不把旧程序响应误认为新代码已生效。
10. 作为开发者，我希望安装依赖或迁移失败时启动命令非零退出，以便避免错误地继续开发。
11. 作为开发者，我希望修复失败原因后可以重试同一命令，以便不必手工重建整套环境。
12. 作为开发者，我希望取消或并发运行命令时锁与任务正确处理，以便不留下无法重试的状态。
13. 作为开发者，我希望不同工作目录或临时测试实例隔离资源，以便不会串用端口、凭据和数据。
14. 作为开发者，我希望普通停止保留持久化数据，以便下次继续使用当前实例。
15. 作为开发者，我希望开发重置明确展示并确认目标，以便只删除本次选择的开发实例数据。
16. 作为开发者，我希望数据库卷存在而凭据丢失时停止操作，以便不被自动生成的新密码破坏现有连接关系。
17. 作为维护者，我希望根工作区直接组织服务与前端应用，以便不增加 backend、frontend 分层。
18. 作为维护者，我希望 Go 模块各自声明依赖且只在仓库内组合，以便避免个人机器路径影响他人构建。
19. 作为前端开发者，我希望多个 app 共用一个权威锁文件，以便依赖解析结果一致。
20. 作为维护者，我希望只在真实复用出现时提取共享能力，以便不先建设空公共框架。
21. 作为维护者，我希望服务和 app 保持清晰的实现边界，以便新增应用不会依赖其他应用的内部源码。
22. 作为开发者，我希望环境配置明确指定并严格校验，以便配置错误不会静默变成默认行为。
23. 作为开发者，我希望本地覆盖是明确的完整替代配置，以便无需理解隐式递归合并规则。
24. 作为部署操作者，我希望 dev、test、prod 的输入和策略明确区分，以便未知环境被拒绝。
25. 作为部署操作者，我希望宿主机遗留环境变量不能改变目标，以便命令实际操作的实例与我指定的一致。
26. 作为部署操作者，我希望 Secret 与普通配置分离，以便凭据不会进入镜像、公开配置或日志。
27. 作为使用者，我希望两个参考应用通过同一个 Nginx 入口访问，以便浏览器路由行为统一。
28. 作为前端开发者，我希望运行时公开配置与静态镜像分开，以便同一镜像可跨 test/prod 使用。
29. 作为使用者，我希望公开配置加载失败时看到明确错误，以便不被静默转向错误接口。
30. 作为使用者，我希望深层路由刷新正常且缺失资源正确返回 404，以便区分应用路由和资源故障。
31. 作为开发者，我希望 API 容器重建后入口代理自动重新发现它，以便无需手工修改地址。
32. 作为部署操作者，我希望共享测试和生产使用提供的 TLS 证书，以便离线环境不依赖在线签发。
33. 作为维护者，我希望应用服务明确区分存活、就绪与外部链路健康，以便健康判断具有实际意义。
34. 作为维护者，我希望应用在终止时有界地停止接流量并处理在途工作，以便容器停止行为可预期。
35. 作为应用维护人员，我希望使用名为 `omega` 的应用运维 CLI，以便统一完成所属应用的维护操作。
36. 作为应用维护人员，我希望 CLI 与 API 使用相同提交和镜像，以便避免维护工具与应用版本错配。
37. 作为应用维护人员，我希望查看帮助、版本和校验配置不依赖数据库，以便在数据库异常时仍能诊断输入。
38. 作为应用维护人员，我希望依赖诊断和健康检查有超时与明确退出码，以便人工和脚本都能判断结果。
39. 作为应用维护人员，我希望查询迁移状态后显式执行前向迁移，以便应用启动不会意外修改数据库结构。
40. 作为应用维护人员，我希望迁移具备互斥、校验和及失败记录，以便避免并发执行或修改已发布迁移造成错误。
41. 作为应用维护人员，我希望系统元数据初始化幂等并核对实例身份，以便重复操作不会改写现有实例。
42. 作为数据库维护人员，我希望初始化、迁移和运行权限分离，以便普通应用进程不能修改数据库结构。
43. 作为部署操作者，我希望写操作核对真实数据库的环境和实例，以便错误参数不能把生产实例当作开发实例。
44. 作为部署操作者，我希望应用拒绝未知或不兼容的数据库结构，以便不在错误版本组合上继续运行。
45. 作为应用维护人员，我希望 CLI 提供可读与结构化输出，以便既能直接操作也能通过脚本集成。
46. 作为维护者，我希望固定经过验证的工具链版本，以便启动和检查不会悄悄升级依赖。
47. 作为维护者，我希望手动质量检查覆盖所有实际模块和 app，以便不会遗漏新加入的工作区成员。
48. 作为维护者，我希望测试关注命令、HTTP 和持久化结果，以便内部重构不会迫使我重写行为不变的测试。
49. 作为发布人员，我希望整套应用使用统一发布版本，以便离线现场不用自行组合服务版本。
50. 作为发布人员，我希望发布包包含所需的应用、组件和工具镜像，以便目标机无需联网补齐依赖。
51. 作为发布人员，我希望包内文件、实际镜像内容和目标平台可以核对，以便损坏或错误架构的交付物被拒绝。
52. 作为发布人员，我希望同一组镜像通过 test 验证后原样用于 prod，以便验证结果对应实际部署内容。
53. 作为部署操作者，我希望目标机不需要源码和开发工具，以便部署不依赖现场编译。
54. 作为部署操作者，我希望缺少镜像时明确失败而不是联网拉取，以便离线部署行为确定。
55. 作为部署操作者，我希望环境配置和凭据独立于发布目录，以便升级不会覆盖目标环境输入。
56. 作为部署操作者，我希望先预检再进入维护窗口，以便减少可提前发现的问题造成的停机。
57. 作为部署操作者，我希望迁移或健康验证失败后保留维护状态和诊断，以便准确知道哪些步骤已执行。
58. 作为部署操作者，我希望只有确认数据库兼容时才允许切回旧镜像，以便回退不会让旧应用访问不兼容结构。
59. 作为维护者，我希望日志有轮转限制且状态输出区分运行与健康，以便诊断不会造成无限磁盘增长。
60. 作为维护者，我希望新增服务、app 或组件时有清晰接入规则，以便工作区、配置、镜像与检查保持一致。
61. 作为验收人员，我希望在阻断外网的隔离环境演练部署，以便真实验证离线能力而非只检查命令参数。
62. 作为验收人员，我希望 macOS 与原生 Linux amd64 分别记录证据，以便不会把模拟运行误报为原生支持。
63. 作为验收人员，我希望每项要求都有明确结果和证据，以便文档存在或代码提交不会被当成验收通过。
64. 作为项目负责人，我希望规格、实施、本机验证和真实生产交付分别记录，以便准确判断工程进度。
65. 作为项目负责人，我希望本次不引入 CI 或备份恢复，以便严格控制已确认的交付范围。
66. 作为项目负责人，我希望先完成规格发布并保持未实施状态，以便在后续明确下达指令后再启动开发。

## Implementation Decisions

1. **工程与参考应用。** 单仓库、根 Go Workspace 和根 Yarn Workspace；一个 api、web/console 两个参考应用、PostgreSQL 和入口 edge。参考应用展示项目、app、环境、版本及接口状态，以必要系统元数据验证数据库访问，不增加业务模型。
2. **组织边界。** 根级服务集合命名为 services，前端应用集合命名为 apps；不设置 backend/frontend 外层。共享 Go 能力和前端包分别按真实需要提取，禁止空框架、服务间导入实现及 app 间引用源码。根不建立统包所有服务的 Go Module；模块地址匹配实际代码仓库，各模块维护自己的依赖，Workspace 只引用仓库内实际成员。
3. **依赖权威来源。** Go 工作区与模块、Yarn 工作区声明与单一锁文件、Compose 拓扑和显式环境配置各自负责所属信息，不建立重复描述整个工程的通用模型。未独立发布的共享 Go 模块允许仓库内相对替换，不承诺仅复制单个服务目录即可构建。
4. **前端依赖。** 使用 Yarn node-modules 安装模式、workspace 内部依赖协议及 immutable 安装。每个 app 提供开发、构建、类型检查、lint、测试能力；只有一个依赖安装写入入口，安装结果、嵌套依赖与安装状态有明确可写位置，不能由两个开发服务器并发修改。
5. **职责划分。** Makefile 为薄入口；脚本负责固定步骤、输入、锁、超时和错误；Compose 管理容器运行关系；omega-api 提供应用服务；omega 只维护所属应用。不要把复杂 Makefile 平移为通用脚本引擎，也不向应用或维护容器提供 Docker 控制能力。
6. **用户命令契约。** 提供 `make dev`、`make down`、`make status`、`make logs`、`make check`、`make test`、`make dev-reset`。make dev 固定属于 dev；维护操作通过薄包装调用同版本 omega。正式调用必须明确环境、实例输入和发布版本。
7. **环境与平台。** 环境仅 dev/test/prod；开发支持当前 macOS arm64 和 Linux amd64，正式 test/prod 限 Linux amd64 单机 Compose。开发与构建可联网；正式部署与运行不依赖外网。不因临时验收而新增一个环境类型。
8. **宿主机前置。** 部署方预装操作系统、Docker/Compose、Bash、curl 和基础文件归档工具；开发额外需要 Git/Make。Go、Node、Yarn 和数据库在容器内运行，正式目标机不需要源码、Make 或宿主机版 omega。额外配置处理工具置于固定工具镜像，预检不得形成依赖未生成配置或 Secret 的引导循环。
9. **实例隔离。** 开发实例 ID 首次生成后持久化，正式实例 ID 显式提供；容器、端口、凭据和数据按实例隔离。项目名及持久卷不随发布版本变化，不使用固定容器名或固定 IP。数据库元数据记录实例 ID 与环境，写操作验证真实记录。
10. **配置类别与选择。** 编排参数、应用配置、前端公开配置和 Secret 分离。应用每次读取明确指定的完整 YAML，前端每个 app 使用完整公开 JSON；本地覆盖为完整替代，不做任意递归合并。test/prod 不接受个人覆盖，未知环境拒绝。
11. **配置校验与污染防护。** 拒绝未知/重复字段、类型错误、非法时长、缺失必填项。Compose 显式选择项目、目录、组合文件及环境输入，并处理继承的 COMPOSE_* 和受控 OMEGA_* 冲突变量，防止遗留 shell 环境改变目标。配置按数据解析，不通过 source 或 eval 执行。
12. **Secret。** 独立文件按容器实际需要挂载并验证权限；API 不挂技术初始化凭据，前端无后台 Secret。首次 dev 可随机生成凭据，已有内容不覆盖；有数据卷而凭据丢失时失败，不生成新密码、不修改数据库。日志、镜像、公开配置和可公开诊断不得泄露 Secret。
13. **容器运行模式。** 开发采用 Go 监听重编译和 Vite；正式采用预构建 API 二进制及各 app 独立静态镜像。edge 不打包全部前端。Compose 按基础关系、开发或正式运行以及环境差异明确组合，检查最终模型；一次性准备任务显式调度。
14. **网络与权限。** 默认仅 edge 发布入口，开发绑定回环地址；数据库只接数据网络，API 连接应用与数据网络，前端不访问数据库。应用容器非 root、限制可写位置与资源，不挂 Docker socket；第三方组件按实际运行要求配置。源码不留下开发者无法编辑的 root 属主文件。
15. **公开 HTTP 契约。** 根 URL 跳转 `/web/`；`/web/` 和 `/console/` 分别承载 app；`/api/` 转发 API 且保留前缀；未声明入口返回 404。参考接口为 `GET /api/v1/ping`，验证外部链路及必要数据库读访问，不能暴露详细内部诊断。
16. **前端运行时配置。** edge 在 `/web/runtime-config.json` 和 `/console/runtime-config.json` 精确返回公开 JSON，响应 no-store。前端先校验 schema、appId 和必填字段，再初始化请求客户端与 React；失败明确显示，不回退默认接口。app 构建 base 与路由固定，运行时配置不能任意改变部署基础路径。
17. **代理与浏览器行为。** HMR WebSocket 经 edge，浏览器不依赖容器地址；服务容器重建后代理重新解析地址。深层应用路由支持刷新，缺失 JS/CSS 返回 404，哈希资源长期缓存，HTML 及时更新。两个 app 属于同一浏览器信任边界，公开开关不代替后端授权。
18. **TLS 与状态。** 共享 test/prod 由 edge 终止 TLS，域名、证书与私钥由部署方提供；只读挂载，检查匹配与有效期，提供受控重载，演练使用测试证书。日志轮转有界，status 报告入口、证书有效期、磁盘和健康，不建设外部监控或通知平台。
19. **开发启动顺序。** 预检并取得实例锁；补齐首次输入；准备固定工具和开发镜像；校验配置及最终模型；启动数据库并技术初始化；需要协调时暂停开发应用；单入口安装锁定依赖；调用 omega 校验、迁移、初始化；启动所有长期服务；等待健康并经 Nginx 验证；输出地址、释放锁并返回终端。
20. **重复执行和错误。** 重复启动允许短暂中断开发应用，但不清空数据、覆盖配置或重置密码。源码自动热更新，依赖/迁移变化由重新运行 make dev 协调。每阶段失败非零退出并报告位置，保留数据与日志；所有等待有超时，取消结束当前任务并释放自己的锁，不删除其他实例资源。带空格的路径必须可用。
21. **停止与重置。** 普通停止保留持久卷。开发重置独立展示并确认实例与资源，核实 dev 归属，只作用于当前实例；test/prod 不提供普通清空入口，也不允许主机范围的无差别清理。
22. **CLI 交付边界。** 命名为 omega，与 omega-api 同 Go Module、同提交、多阶段构建进入同一正式镜像。开发调用当前源码，正式调用指定发布镜像的一次性容器。维护只初始化所需组件，不顺便启动 HTTP 或业务任务，不加入 Docker、构建、部署和任意 SQL 执行功能。
23. **CLI 命令。** 支持 version、config validate、doctor、health check、db status、db migrate、data ensure。帮助和版本不连接数据库，配置校验也不连接数据库；诊断有超时。data ensure 仅幂等初始化必要安装身份等系统元数据，不预造账号、权限或业务字典；无真实需求时不增加空壳维护命令。
24. **CLI 输出与退出码。** 支持可读及 --json 输出，结果写 stdout、诊断写 stderr；退出码为 0 成功、2 参数/配置错误、3 目标/策略拒绝、4 执行失败、5 超时/不健康、6 互斥冲突、130 取消。记录操作 ID、版本、实例、命令、起止时间和结果，不记录 Secret。非交互确认不能绕过目标、权限或兼容检查。
25. **数据库技术初始化。** 角色分为技术初始化、应用迁移和应用运行所需权限。技术初始化准备数据库及角色，不建业务表，不能在每次升级时重跑整套初始化；迁移角色负责 schema，运行角色不能修改 schema。当前对象权限及未来默认权限必须验证。
26. **迁移契约。** API 正常启动不自动迁移，由 omega 显式执行前向迁移。已发布迁移不可原地修改；有版本记录、校验和、互斥、失败诊断和超时。V1 自动流程只支持事务内迁移，失败回滚当前事务，不跳版本或伪装成功。事务回滚不是备份恢复功能。
27. **兼容性与身份。** API/CLI 声明并经测试支持的 schema 范围，未知、更高或不兼容状态拒绝启动/回退；不能仅修改声明掩盖不兼容。首次空库的身份初始化是明确步骤，已有身份不得改写环境；空库、部分初始化、元数据异常和不匹配必须区分。
28. **生命周期。** 应用依次完成配置、资源及身份/schema 检查后进入 ready；初始化失败逆序清理。关闭时退出 ready，停止接流量，等待在途工作并有界释放资源，容器宽限时间大于应用关闭预算。liveness、readiness 和外部 smoke 分开；依赖暂不可用不必直接退出进程，不假设 unhealthy 自动触发重启。
29. **工具链。** 固定经实测兼容的正式版本，Node 采用 LTS，TypeScript 选 6.0.3 与匹配 lint 工具，Yarn 使用 node-modules。正常启动及检查不更新依赖或锁文件，不运行会修改依赖文件的整理操作；依赖维护单独执行。其他精确版本须在实现时完成兼容验证，候选列表不算测试通过。
30. **手动质量检查。** 不创建 CI。操作者调用统一脚本覆盖全部实际 Go 模块和前端成员的格式、类型、静态检查、测试、依赖一致性与正式构建，并检查三环境最终模型及版本声明一致性。发布镜像不用 latest，正式模型拒绝源码挂载、开发服务器、现场构建、多余管理权限及明文凭据。
31. **统一发布单位。** api、web、console、edge 和所需工具/基础组件形成统一发布版本，各镜像仍独立构建。普通应用发布不包含 PostgreSQL 大版本升级。所有正式镜像及部署工具镜像满足 Linux amd64 目标。
32. **离线包内容。** 包含镜像归档、正式编排和代理材料、无真实凭据的配置模板、本地部署/维护入口、版本与源提交、兼容要求、镜像内容身份及平台、文件校验值和证据。排除源码、开发镜像、依赖安装结果、真实 Secret、私钥和数据库数据。目标配置独立于发布物，升级不覆盖。
33. **离线身份核验。** 导入后核对实际镜像内容 ID 和平台；唯一版本标签只是本地引用，不能只相信标签。远端 registry digest 可作来源信息，不假设归档导入后必然可离线用该远端引用。SHA-256 验证损坏或与可信预期不一致，清单须经可信渠道传递，不把同包校验和称为发布者签名。
34. **产物提升。** 构建一次，候选镜像通过 test 后原样用于 prod；前端环境差异来自公开配置。证据对应同一候选镜像清单，添加证据或归档外层不触发镜像重建。发布物和实际部署版本必须可追溯。
35. **发布顺序。** 明确目标并预检/加锁；校验包、架构、磁盘、环境输入、证书和 Secret；导入并核验镜像；验证禁止拉取和构建的最终模型；首次部署技术初始化或升级核对已有实例；进入维护窗口停止写入；执行兼容检查、迁移和必要元数据初始化；更新应用并验证 readiness 与外部 smoke；成功后退出维护并记录结果。
36. **离线及失败约束。** 缺镜像直接失败，不隐式拉取或现场构建；运行时资源也不依赖外网 CDN。多容器发布不伪装成事务，失败保留维护状态及已完成步骤、实际版本、数据和诊断，不清空卷或降级数据库。旧镜像仅在其自身兼容声明、实际数据库与配置核对通过后显式切回，否则停止并报告，后续修复另行处理。
37. **扩展规则。** 新服务需同步接入工作区、镜像、编排、配置、健康、检查和文档；新 app 同步工作区、固定路由、公开配置、依赖挂载、HMR、静态镜像、代理和检查。新组件需明确权限、数据、健康和失败行为。共享库按实际复用提取，omega 不成为直接维护其他服务数据库的中央入口。

## Testing Decisions

1. **已确认的测试边界。** 用户已确认完整方案中的命令入口、浏览器链路与离线部署验收；本规格沿用这些边界，不新增访谈或内部测试接口。主要测试入口是一套隔离的运行实例，通过操作者使用的命令及 Nginx 对外 HTTP/浏览器入口观察结果；CLI 专属退出码和无数据库副作用行为从 omega 进程边界验证。
2. **好测试的标准。** 验证外部行为、退出码、输出、HTTP 结果、资源归属及必要持久化结果，不绑定内部函数、调用次数、目录细节或任意等待时长。关键集成场景使用真实 PostgreSQL、Compose 和 Nginx；仅对难以在高层精确覆盖的配置和兼容规则补少量模块测试。
3. **现有先例。** 当前仓库没有应用代码或既有测试框架，不能声称复用现有测试。测试入口优先沿用已确认用户操作契约，不为测试创建额外服务或生产后门。测试会覆盖参考 API、两个 app、omega、配置/身份、迁移权限、编排脚本、代理以及发布包。
4. **环境与数据隔离。** 使用专属项目名、端口、卷和临时环境输入，只清理测试自身资源；有数据库卷但凭据丢失、实例不匹配等负例不得作用于真实用户实例。离线演练在隔离目标 Docker 环境阻断外网并验证阻断有效，不修改开发者整机网络。
5. **成功与失败同时覆盖。** 冷启动、重复启动、重建代理、迁移和离线导入要有成功路径；锁冲突、取消、配置错误、凭据丢失、依赖失败、迁移失败、包损坏、缺镜像、不兼容回退和健康失败要验证明确拒绝及保留状态。单纯检查脚本存在或 mock 返回成功不足以验收。
6. **平台证据。** macOS arm64 和原生 Linux amd64 分别执行并记录源码提交、命令、版本、结果和证据。模拟 amd64 单独标记，不能替代原生结果。尚无原生目标机执行证据，届时未执行项保持未完成，不能通过缩小报表暗示已支持。
7. **手动执行与完成判定。** 所有检查和浏览器/部署演练通过手动触发的统一脚本运行，不依赖 CI。以下编号沿用已确认方案；结果使用未执行、通过、失败、范围排除。每个适用编号必须有证据，当前均未实施验收。

## Out of Scope

- 本轮工程实现、安装依赖、启动容器、构建镜像、运行验收及实际部署；当前只编写并发布规格。
- 备份、恢复、恢复演练、备份调度、保留与异机副本、RPO/RTO，以及将升级前备份设为发布门槛。
- GitHub Actions 或其他 CI/CD 流水线；保留手动运行的质量检查和部署脚本。
- 真实生产服务器交付、零停机发布、多主机调度、高可用集群、Kubernetes 和服务网格。
- 工程管理 CLI、动态配置平台、通用发布/断点恢复引擎、自动 SSH 分发平台和宿主机工具安装器。
- 未定义的业务、账号、权限、业务字典、任意 SQL 维护入口、微前端或跨域隔离体系。
- PostgreSQL 大版本升级、事务外迁移自动化，以及自动数据库降级。
- 原生 Windows/WSL2 和 Linux arm64 正式部署的支持承诺；macOS 上 Linux arm64 开发容器不改变正式目标架构。
- 默认建设外部监控、通知渠道或在线证书签发服务；不把同包校验和宣称为发布者签名。
